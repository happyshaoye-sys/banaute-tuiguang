## 历史 v2.56 核心变更（缓存自动失效，运营界面无变化）

- **把「取数 schema 指纹」编进两层缓存**：① 解析层缓存（`_parsed/<md5>.pkl`）的缓存键加入指纹；② 日事实缓存与共享维度缓存的载荷增加 `schema_fingerprint` 字段并在读取时校验。指纹 = `core/schema.py` 的源分类规则 / 列名别名 / `WUJIE_REMAP` + `core/loader.py` 的「源类型→允许列」白名单，内容是稳定哈希（`schema_fingerprint()` / `source_schema_fingerprint()`）。
- **为什么**：v2.55 修「计划名称」时踩过一次——白名单放行了 `计划名字`，但两层缓存只按「版本 + 路径 + 大小 + mtime」命中，源文件没变就一直命中旧结果，表现为"改了没生效"，只能靠人工记得升两个版本号。现在改白名单/别名 → 缓存**自动失效**。
- **本次不会触发重建**：旧载荷没有 `schema_fingerprint` 字段时按**兼容命中**处理（不与版本换代叠加），所以 2.55 已付过的那次约 6.5 分钟重建不会再来一次；从本版起写入的载荷都带指纹。
- 门禁新增契约：解析层缓存键必须含 schema 指纹、日事实缓存必须校验 `schema_fingerprint`、`core/schema.py` 必须提供 `schema_fingerprint()`。
- 验证：全量单测 363 项（新增 3 项：指纹随白名单变化、解析层缓存键随指纹变化、日事实载荷指纹不一致即未命中）＋运行时实测缓存命中率不下降。

## 历史 v2.55 核心变更（修复 2.54 未生效的「计划名称」）

- **根因**：「计划名称」为空的真正原因不在汇总层，而在**取数白名单**——`core/loader.py` 的 `SOURCE_WUJIE_SUBJECT`（无界-商品主体）白名单里没有 `计划名字`，源文件里明明有这一列（实测表头第 7 列，如 `CS_RQ_短外套合集控成交`），却在读文件时就被丢掉了。2.54 在 `core/merge.py` 里做的汇总改动因此拿不到值。
- **修复**：① `SOURCE_WUJIE_SUBJECT` 白名单加入 `计划名字`；② 解析层缓存版本 `PARSED_CACHE_VERSION v11 → v12`；③ 日事实缓存版本 `DAILY_FACT_CACHE_VERSION metox2.39-daily-facts-v3 → metox2.55-daily-facts-v4`。
- **为什么必须同时升两个缓存版本**：两个缓存都只按「版本 + 文件路径 + 大小 + mtime」命中，源文件没变就一律命中——只改白名单不升版本，缓存会继续返回**旧列集合**的帧，修复看起来"没生效"。
- **影响面**：首次运行会重建缓存（集团店 56 天实测：解析层与日事实全部未命中，`批量加载 115 秒 / 总计 134 秒`），之后恢复热缓存速度（8 秒/26 秒量级）。重建只做一次。
- 交付后的可见效果：执行表 `推广明细` 文本带 `计划名:…`、`推广计划全量明细` 带计划名称、预算决策看板「推广计划管理」与「导出全部Sheet」的 `计划名称` 列有值。

## 历史 v2.54 核心变更

- **主推线性能：冻结后默认只加载 28 天**。角色判定只需要近 7 日 + 上一 7 日（14 天），同层基准要 28 天；56 天（7 天窗口 × 8 窗）只是"现场算引擎建议"才需要。阈值已由运营冻结时，主流程不再补 56 天（实测冷跑 56 天约 365 秒 → 28 天约省一半；热跑 41.7 秒 → 约 32 秒）。
- **新增轻量历史缓存**（`core/role_history_cache.py`，工具目录 `cache/`）：`metox_gmv_daily_{年}_{店}.pkl`（只存每天 `宝贝ID→GMV`）与 `metox_kpi_daily_{年}_{店}.json`（只存每天 6 个 KPI 数），按"年份|店铺"分键、保留最近 70 天、原子写、损坏即安全返回空。GMV 抽取与 `day_map` 入口统一走 `budget_role.gmv_by_product`，两条路径有单测锁定逐位一致。

- **看板「日趋势」图仍是 56 天**：冻结后只加载 28 天时，用逐日 KPI 缓存补回历史，趋势图不变短。
- **新品视图新增第 4 个子页签「新品变化」**（`core/new_product_change.py`）：快照 + 差分，类型为 **真上新 / 历史补发现 / 消失 / 恢复在线 / 观察中（离线1天）**。口径：真上新＝首现日晚于上次快照日；补发现＝本次才进索引但首现日不晚于上次快照日（不算上新）；消失＝上次在线且本次非在线或不再出现、**连续 2 个自然日**（按自然日算）；恢复在线＝以前发现过、上次不在线、本次重新在线（不算全新款）。基线可切 `上次运行 / 3 天前 / 7 天前（上周同期）/ 14 天前`，快照保留 30 份，消失款也带款式主图，另给 5 个汇总卡片与独立 CSV 下载。三条边界：**源缺失日不算消失**（整天源不可用则不判定且不写快照）、**回填历史不推进快照**、粒度是**款式键**（多链接任一在线即在线）。
- **清理规则护栏**：`衰退预警`（36 宫格位置变化的弱信号）单独命中不再直接判"清理 + 禁止加投"——若 `近7日日均GMV ≥ TH_MID` **或** `GMV趋势率 ≥ 0` 则放行给正常瀑布判定，依据里写明"清仓护栏放行：…"；`清退 / 清仓 / 衰退期 / 淘汰 / 观察期` 等强标记照旧判清仓。角色算法版本 `role-waterfall-v3 → v4`。
- **日趋势横轴改为「年-月-日」**（原先图表自动格式化为 `Sep 11` 这类）。
- **「推广计划管理 / 推广明细」补回计划名称**：`core/merge.py` 的明细聚合此前没把 `计划名字` 带进记录。
- **打包随带阈值冻结登记**：`scripts/release_metox.py` 随包分发 `config/`；`threshold_store.default_freeze_root` 在没有 `.git` 的第三方包里也优先读随包 `config/threshold_freeze.json`（可直接继承发来的已冻结阈值），既无仓库也无随包登记时才回退 `cache/`。

## 版本治理

- `VERSION.json` 是唯一版本源。
- `core/version.py` 从唯一版本源派生页面显示版本。
- `scripts/release_check.py` 检查业务规则变更是否升版，并校验页面、文档、分支和阈值契约。
- `scripts/release_metox.py` 先执行发布检查，再生成带版本和日期的不可覆盖目录与 ZIP。
- Git 发布标签使用 `MetoX<版本>`，例如 `MetoX2.2`。

## 核心文件

- `core/metox_algorithm.py`：MetoX 内置算法。
- `core/v93_signal.py`：v9.3 日报信号解析。
- `core/segmentation.py`：36 宫格、风险标签、动作和优先级。
- `core/analysis.py` / `core/exporter.py`：页面和 Excel 分析口径。
- `core/merge.py` / `core/periods.py`：数据合并和周期聚合。
